# Confidence scoring + online pipeline wiring for M1 (final review)

This branch wires the previously-isolated stages into a runnable M1 pipeline and adds the confidence layer that decides which extractions to trust. `config/settings.py` reads the §17 env vars into a typed `Settings` (money magnitudes as `Decimal`, model knobs as `float`); `clients/factory.py` maps a provider id to a live `VLMClient` with lazily-imported vendor SDKs; `pipeline.py` sequences preprocess -> triage -> extract(+repair) -> normalize and adapts that to the eval harness; `score/confidence.py` folds every uncertainty signal into a single `Decimal` per the §12 penalty table and routes it. `eval/run_baseline.py` is the one-command runner that composes settings -> client -> pipeline -> harness. The §12 math, the routing override, the Decimal discipline, and the lazy-import guarantee all hold up under inspection and are exhaustively unit-tested.

Watch for: the `is_handwritten` penalty reads only the model-declared `receipt.meta.is_handwritten` and ignores triage's own handwriting classification, so a receipt triage flags as handwritten but the extractor doesn't can miss the -0.15 (confirmed, prefer-doubting risk); the 0.85/0.60 thresholds now live in three independent places and only one is wired (confirmed); and `run_receipt` validates the raw extraction but returns the normalized one, so the bundled report can disagree with the returned extraction on an ambiguous date (confirmed, errs conservative).

**Verdict**: APPROVED

## High-level view

Scoring is the heart of the change and it is faithful to §12: start at 1.0, apply a flat -0.35 for any error, bounded per-item penalties for warnings/ambiguous-fields/consistency-disputes/triage-issues, fixed penalties for legibility, handwriting, and each missing critical field, one small merchant bonus, then clamp to [0,1] and quantize to three decimals. The scorer is pure and `Decimal`-only, and `explain_confidence` shares the exact signal list with `score_confidence` so the human-readable reasons can never drift from the number.

The one scoring nuance worth a second look: the `is_handwritten` penalty reads only the extractor's `meta.is_handwritten`, not triage's derived flag — within spec latitude, but the less conservative of the two sources.

Routing matches the §12 table including the "errors + null total -> urgent" override, which is a logical AND. It's correct, but note that `route()` isn't wired into the eval path yet (the harness gates on a raw threshold compare), and the auto-approve/review thresholds are now duplicated across `route()` defaults, `Settings`, and `eval.metrics.AUTO_APPROVE_THRESHOLD`. No drift today because only the metrics constant is on the live path; M3 needs to consolidate before `route()` goes live.

The factory keeps the core offline-importable: `clients/__init__.py` is empty, `base`/`fake` pull no SDK, and `anthropic`/`openai` are imported inside their construction branches (and again inside the client constructors). `VLM_BASE_URL` correctly overrides the per-provider default for the OpenAI family and is verified by test; it is silently ignored for `anthropic`, and every OpenAI-family provider (including self-hosted vLLM/Ollama) requires `VLM_API_KEY`.

Integration is sound: `build_eval_pipeline` returns exactly the `Callable[[Path], tuple[ReceiptExtraction, Decimal]]` the harness expects, `run_baseline` refuses the response-less default `fake` provider early with an actionable hint instead of failing deep in the pipeline, and secrets stay out of the repo (`.env` is untracked and gitignored). 285 tests pass and `ruff check .` is clean, both confirmed locally.

### The §12 penalty table, verified against the spec

The constants in `confidence.py` map one-to-one onto the §12 table: flat `-0.35` for any error (applied once via `if report.has_errors`, not per-error), `-0.08`/warn capped at `-0.30`, `-0.10`/`-0.25` for fair/poor legibility, `-0.15` handwritten, `-0.30`/`-0.10`/`-0.10` for null total/date/merchant, `-0.05`/ambiguous capped at `-0.20`, `-0.06`/dispute capped at `-0.30`, `-0.03`/triage-issue capped at `-0.10`, and the lone `+0.05` merchant bonus at `>= 10` priors. `_capped(per_item, count, cap)` returns `max(per_item * count, cap)` — both operands negative, so `max` is the correct bound toward zero — and short-circuits to zero for non-positive counts. The final `min(_ONE, max(_ZERO, total)).quantize(_QUANTUM, ROUND_HALF_UP)` clamps then rounds to three decimals; since every penalty is at most two decimals and counts are integers, the quantize is exact rather than lossy. `test_confidence.py` pins each with hand-computed expectations (3 warns -> 0.760, 5 warns -> 0.700, 6 ambiguous -> cap -> 0.800, error+warn+warn+nulls+handwritten+poor -> clamp 0.000).

Consistency disputes are counted only when a `ConsistencyResult` is actually supplied (`consistency is not None`), so the straight-line M1 path passing `consistency=None` contributes nothing — matching the note that self-consistency lands in M6. The guard matters: a cache- or default-manufactured empty consistency result must not be read as "no disputes = high confidence."

### `is_handwritten`: extraction meta vs triage

`_signals` reads `receipt.meta.is_handwritten` for the `-0.15`. `TriageResult` carries its own `is_handwritten` property (derived from `document_type`/`print_type`) and it is not consulted here. The extractor's flag defaults to `False`, so if the extraction model doesn't set it while triage classified the document as handwritten, the penalty is silently skipped. The blast radius is bounded — handwritten receipts usually also draw a fair/poor legibility penalty, and M6 will add consistency disputes — but given the prime directive optimizes for auto-approval precision, the safer read is `receipt.meta.is_handwritten or (triage is not None and triage.is_handwritten)`. Spec §12 lists the signal without naming its source, so this is a design choice rather than a violation.

### Routing override and threshold triplication

`route()` implements the §12 table exactly, including the urgent override as a logical AND (`report.has_errors and receipt.totals.total is None -> priority 0`). That AND is subsumed by the penalty math for auto-approval purposes: an error (`-0.35`) plus a null total (`-0.30`) caps confidence at 0.35, well under 0.85, so the override can never flip a receipt out of the auto-approve set — the harness computing auto-approval from a raw `confidence >= threshold` therefore doesn't leak precision by skipping `route()`. The concern is forward-looking: `route()` is not on any live path yet (only tests call it), and the 0.85/0.60 pair now exists as `route()` keyword defaults, `Settings.auto_approve_threshold`/`review_threshold`, and `eval.metrics.AUTO_APPROVE_THRESHOLD`. When M3 wires routing/persistence, these must resolve to one source — most naturally `Settings` — or a retune in one place will silently disagree with the others.

### Validate-raw, normalize-after

`run_receipt` calls `extract_with_repair` without a `normalize_fn`, so validation (and therefore the repair loop's decisions and the returned `report`) runs on the raw extraction; normalization is applied only to the winning attempt afterward. This is exactly the order the M1 milestone specifies ("...extract_with_repair -> normalize"). The observable consequence is narrow: `normalize()` can null an ambiguous date (step 3), and since `score_confidence` reads the normalized extraction's `date` while the `report` reflects the raw one, the score can carry a `-0.10` date-null penalty that has no corresponding finding in the bundled report. Money is never touched by `normalize`, so the total-null penalty and the routing override stay consistent. The direction is conservative (confidence only drops), and within the eval path the returned extraction and its confidence are both computed post-normalization. Worth reconciling only when M3 starts persisting the report and the extraction side by side.

### Factory: lazy SDKs, base_url precedence, key requirement

The lazy-import guarantee holds at two levels: `clients/__init__.py` is empty and neither `base` nor `fake` imports a vendor SDK, so importing `factory` (or the whole `receipts` core) pulls in nothing from Anthropic or OpenAI; and the `from .anthropic_client import ...` / `from .openai_compat import ...` statements sit inside the matching provider branch, with the actual `import anthropic` / `import openai` deferred again into the client constructors. `VLM_BASE_URL` overrides the provider default for the OpenAI family (`settings.vlm_base_url or _OPENAI_BASE_URLS[provider]`) and both the override and the fallback are asserted against the constructed client's endpoint.

Two edges: `VLM_BASE_URL` is only consulted on the OpenAI-family branch, so setting it with `vlm_provider="anthropic"` has no effect — reasonable given the branch scope, but silent. And `_require` demands `VLM_API_KEY` for every OpenAI-family provider, including self-hosted `vllm`/`ollama` that typically accept any token; the underlying OpenAI SDK does insist on a non-empty key so a placeholder satisfies it, but the "requires VLM_API_KEY to be set" message could send a local-only user hunting for a key they don't have.

### run_baseline: refusing the response-less fake provider

The default `fake` provider is built as `FakeVLMClient([])` — no scripted responses — so on the `client=None` (env-derived) path `run_baseline` raises early with a message naming `VLM_PROVIDER`/`VLM_API_KEY`/`VLM_MODEL_EXTRACT`, rather than letting the pipeline fail deep inside with an opaque "exhausted responses" error. An injected client (the test seam) bypasses the refusal and runs fully offline. The one soft spot is cosmetic: `_latest_results_file` re-derives the just-written path by newest mtime rather than threading it back from `run_eval`, a display-only guess if two runs collide in the same second under the same prompt version.

### Decimal discipline

Every value on the money and score path is `Decimal`: the confidence score, the `Settings` thresholds and plausibility ceiling, and the penalty constants. `Settings` is explicit about the distinction — `consistency_temperature` and `tall_receipt_aspect` are genuine `float` model/image knobs, not amounts — and `test_settings.py` asserts the thresholds land as `Decimal` from env strings with no float round-trip. The harness coerces an incoming confidence back to `Decimal` defensively. Floats appear only at the display boundary (`format_report`'s percentage rendering) and in the §16 statistical ratios. The deferred move of the penalty weights into `config/rules.yaml` (P3.T6) is acknowledged in the module and is out of scope for this branch.

### Test coverage

`test_confidence.py` isolates every penalty, both caps that bite and stay silent, the clamp floor, three-decimal quantization, the bonus threshold on both sides of 10, and all four routing outcomes. `test_client_factory.py` covers fake/unknown/missing-key and both base_url paths. `test_pipeline.py` runs the runner and the eval adapter end to end on a synthetic image with a scripted fake client, and asserts the triage-then-extract call order. `test_run_baseline.py` covers the injected-client happy path and the fake-provider refusal.

Not tested: the normalize-nulls-an-ambiguous-date divergence between the returned report and extraction; a triage-says-handwritten / extractor-says-not case for the `is_handwritten` penalty; and `score_confidence` with `triage=None` (handled in code, never produced by the pipeline since `triage()` falls back to defaults). None are blocking, but the first two correspond directly to the design observations above.
