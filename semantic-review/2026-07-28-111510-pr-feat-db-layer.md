# Persistence layer for the seven-table schema (feat/db-layer, final pre-merge review)

Ten commits add the whole of Phase 3's storage surface: a SQLAlchemy 2.0 ORM for the seven tables in §6, an Alembic revision that creates them, a repository layer implementing §14.8 (save/query/dedupe/corrections), a review queue implementing §14.9, and two new XLSX sheets with the §13.5 formatting pass. The design is deliberately layered — pure decision helpers stay in `ingest/dedupe.py` and `score/confidence.py`, and the new code only supplies candidates and writes rows — and portability comes from type variants (`sa.Uuid`, `JSON`/`JSONB`) rather than per-backend branching. 389 tests pass, `ruff` is clean, and the suite never touches a network or a Postgres driver.

Watch for: `_coerce_money` accepts `Decimal("NaN")` and `Decimal("Infinity")` (**confirmed**), which on SQLite silently nulls the money column while the corrections audit row records `NaN` as the new value — the audit trail lies about what was stored. `redact_pan` misses at least three PAN shapes that reach `extraction_runs.raw_response` verbatim, including `CARD NO.4111111111111111` (**confirmed**), which is exactly what a thermal receipt prints. `enqueue_review` accepts priority `-1`, the sentinel `route()` returns for "no review needed" (**confirmed**). `alembic upgrade head` needs numpy and Pillow, which are in an optional extra (**confirmed**).

**Verdict**: NEEDS_CHANGES

## High-level view

PAN redaction is the §18 hard rule and it is the weakest part of the branch. The regex is carefully built to stay silent — consistent-separator backreferences, lookarounds that refuse to split a decimal — but the same lookbehind that protects `1234567890123.45` also blocks a PAN printed immediately after a period, and the recursive walk covers dict *values* while never touching dict *keys*. Three shapes leak the full number into an audit column meant to be safe to keep for months.

`_coerce_money` is the one place a reviewer's value is admitted to the money path, and it correctly refuses `float`. It does not refuse non-finite `Decimal`s. `Decimal("nan")` is a legal Decimal, so `"nan"` in a patch parses, passes the guard, and lands in a `Numeric` column: NULL on SQLite (the money is wiped, no error, no flag) and a real `NaN` on Postgres (every later comparison and sum is poisoned). The `corrections` row written alongside says `value_after = "NaN"`, so the audit trail no longer matches the row it describes.

`apply_corrections` otherwise earns its "transactional" label: resolving and coercing every path before mutating anything means an unmappable path leaves the database untouched, and a failure at commit time rolls the whole patch back. Two sharp edges remain — swapping two line-item positions surfaces a raw `IntegrityError` rather than the documented `ValueError`, and because the function owns the session's transaction it also commits any unrelated work the caller had pending.

Money survives the ORM boundary as `Decimal` at full precision, including on SQLite where values round-trip through float: `Numeric(14,4)` fits inside float64's exact range and the result processor re-quantizes on the way back. `find_duplicate_by_content` keeping the total comparison in Python is the right call, but the stated reason — that this keeps it "an exact `Decimal` comparison" — does not hold on SQLite, where the candidate value already made the float trip. What makes it safe is the re-quantization, and the docstring should say so before someone pushes the filter into SQL on the strength of a reason that is not true.

`next_task` uses the standard `ORDER BY ... LIMIT 1 FOR UPDATE SKIP LOCKED` claim, with the capability decided in Python precisely because SQLite drops a locking clause silently instead of erroring; the compile-both-dialects test proves both directions offline. The queue's problems are at its edges: `enqueue_review` does check-then-insert against a UNIQUE column, so concurrent enqueues raise the `IntegrityError` the docstring promises they won't, and it accepts negative priorities including the `-1` that `route()` uses to mean "do not review this".

The drift guard is real but SQLite-shaped. `compare_metadata` against a migrated SQLite file catches an added column, a changed `Numeric` scale, a dropped index. It cannot catch anything that only exists on Postgres — most importantly a new enum member, which shows up as a `VARCHAR` width on SQLite and as a `CREATE TYPE` value list on Postgres. Adding a `ReceiptStatus` value stays green locally and fails at insert in production.

`docker-compose.yml` is documented as dev-only, but `ports: - "5432:5432"` publishes on all interfaces with `receipts`/`receipts` as the credentials, on a database that will hold receipt PII. `127.0.0.1:5432:5432` keeps it usable locally without exposing it to whatever network the laptop joins.

The layer has no production caller yet. `pipeline.py` does not import `receipts.persist`, and nothing outside tests calls `save_extraction`, `enqueue_review`, or constructs a `ReceiptExportRow`. That is the expected shape for a layer-first branch with wiring as the next milestone, but the pipeline-level invariants ("nothing is silently dropped", "every receipt reaches a terminal state") are therefore not enforced anywhere yet, and the `route()`/`enqueue_review` priority mismatch is latent rather than exercised.

### PAN redaction: the shapes that get through

The regex is built with the right instinct. Separators must be *consistent* via a backreference, so `"qty 2 x 18.00"` is not swept into a match; the trailing `(?!\d)(?!\.\d)` refuses to mask the integer part of `1234567890123.45` or to partially mask a longer digit run. The silent cases are tested, which is the harder half of the job. Three shapes still leak, each confirmed against the built pattern:

```
redact_pan("CARD NO.4111111111111111")     -> "CARD NO.4111111111111111"     # leaks
redact_pan("CARD 4111 1111-1111 1111 OK")  -> "CARD 4111 1111-1111 1111 OK"  # leaks
redact_pan({"4111111111111111": "x"})      -> {"4111111111111111": "x"}      # leaks
```

The first is the one that matters. `(?<![\d.])` exists to stop a match starting mid-number, but it also rejects any PAN whose preceding character is a period — and `CARD NO.`, `ACCT NO.`, `REF.` are exactly how a receipt prints the field a VLM is transcribing. The trailing lookahead already prevents the decimal-fraction confusion, so the leading `.` in the lookbehind is doing harm that `\d` alone would not.

The second is narrower but plausible from OCR of a worn thermal print, where one of three separators reads as a different character. Neither the 4-4-4-N branch (backreference fails) nor the unseparated branch (each group is only four digits) matches, so nothing is masked.

The third is a gap in the walk rather than the pattern: `{key: redact_pan(item) for key, item in value.items()}` recurses into values and copies keys through untouched. `_json_safe` has already coerced every key to `str`, so redacting keys is a one-line change with no type risk.

Two scalar types also pass through unhandled — a `float` is returned as-is, and a `set` matches no branch and falls through to `return value`. In the `save_extraction_run` path `_json_safe` runs first and converts sets to lists, so the pipeline is covered; but `redact_pan` is in `__all__`, re-exported from `receipts.persist`, and documented as "strip full card numbers out of `value`", so a future review-UI or logging caller handing it a raw dict gets no protection for those two types.

The false-positive side is in better shape: money, hashes, 4-digit last4, dates, and phone-style numbers are all left alone, and the one accepted false positive — a 13-19 digit all-numeric identifier — is documented as accepted. Worth knowing that this does fire on 13-digit epoch-millisecond timestamps and long trace ids, and that masking an `int` returns a `str`, changing that field's JSON type in the audit row.

### NaN on the money path, and an audit row that disagrees with the column

`_coerce_money` is the gate for every reviewer-supplied amount. It refuses `float` with a clear message and refuses `bool` before the `int` branch can catch it. The gap is that `Decimal("nan")` and `Decimal("inf")` are *valid* Decimals — they raise nothing — and the `isinstance(value, Decimal)` fast path at `repository.py:585` returns a caller-supplied non-finite Decimal without inspecting it.

Observed end to end on SQLite:

```
apply_corrections(s, rid, {"totals.total": "nan"}, "rev")
# receipts.total   -> None            (SQLite converts REAL NaN to NULL)
# corrections row  -> ('totals.total', '10.0000', 'NaN')
```

Two invariants break at once. A money value is destroyed with no error and no flag, which is the opposite of "prefer null over a guess" — this null is not a preserved uncertainty, it is a lost number. And the audit row claims the new value is `NaN` when the column holds NULL, so the corrections table stops being a reliable record of what a reviewer did. On Postgres the shape differs but is not better: `numeric` accepts `NaN`, it persists, and every downstream `==`, `>=`, and `sum()` involving that receipt starts returning surprises — including the tolerance comparisons the validator exists to make trustworthy.

### apply_corrections: the plan/apply split holds; the commit boundary is where it bites

The rollback path is genuinely exercised, and holds for failures that only surface at commit. Correcting `line_items[0].position` to `1` while `line_items[1]` still holds `1` produces:

```
IntegrityError: UNIQUE constraint failed: line_items.receipt_id, line_items.position
after: [(0, 'A'), (1, 'B')]  status auto_approved  corrections 0
```

Nothing partial persists. But the raised type is `IntegrityError`, not the `ValueError` the docstring promises for a patch that cannot be applied, and the operation is legitimate: priority-1 review is a "full re-key", and reordering line items is a normal part of one. A non-deferrable unique constraint cannot survive a swap applied as two statements; `DEFERRABLE INITIALLY DEFERRED` on Postgres, or detecting a permutation and staging through a temporary offset, are the usual ways out.

One more consequence of owning the transaction: `session.commit()` at `repository.py:787` commits everything pending on that session, not only the planned changes. A caller that staged an unrelated write and then called `apply_corrections` gets it committed as a side effect. The docstring explains *that* the function is transactional, not that its transaction is the caller's whole session.

Path semantics deserve one note. `line_items[i]` here addresses the item at *position* `i`, which the docstring states plainly — but `flatten()` is shared with the consistency diff and the eval harness, where `line_items[i]` is a *list index*. The same path string means two different things depending on which module consumes it. Since `_build_line_items` falls back to list order only when emitted positions collide, a model that emits 1-based positions makes `line_items[0]` address nothing and raise. Failing loudly is the right failure, but the collision of meanings will surprise whoever writes the review UI's patch builder.

### The drift guard, and what it cannot see

`compare_metadata` against a freshly migrated SQLite file catches an added or dropped column, a rename, a changed `Numeric` scale, a missing index. The companion test that inspects `ON DELETE CASCADE` and the pair-unique directly is the right addition, since those are exactly what autogenerate does not compare.

What it cannot see is anything that exists only on Postgres. `compare_server_default` is not enabled, so the `server_default=sa.func.now()` columns are unchecked. More importantly, `sa.Enum` renders as a plain `VARCHAR` on SQLite (no CHECK constraint — `create_constraint` defaults off in SQLAlchemy 2.0), while on Postgres it is a native type whose value list is hardcoded in the revision at `alembic/versions/b9342906a5a6_...py:100`. The ORM derives the same list via `values_callable`. Add a member to `ReceiptStatus` and the two drift apart: on SQLite the only observable change is a `VARCHAR` length that may not even move, so the guard stays green, and production fails at insert with `invalid input value for enum`. A direct assertion comparing each `_token_enum`'s member values against the revision's literal list covers it with no Postgres driver.

### Migrations depend on the image-processing stack

`alembic/env.py` does `from receipts.persist import Base`. That executes `persist/__init__.py`, which eagerly imports `repository`, which imports `..ingest.dedupe`, which imports numpy and Pillow. Confirmed: after `import receipts.persist`, both are in `sys.modules`.

Base dependencies are `alembic`, `pydantic`, `pydantic-settings`, `pyyaml`, `sqlalchemy`. Pillow lives in the optional `pipeline` extra and numpy is not declared at all (it arrives transitively via `opencv-python-headless`). So `pip install -e .` followed by `alembic upgrade head` fails on an import that has nothing to do with schema — precisely the install a migration job in a container would use. Importing `receipts.persist.models` instead does not help while `persist/__init__.py` pulls `repository` at import time, since the parent package runs either way; the fix is either lazy imports in `persist/__init__.py` or declaring numpy and Pillow as base dependencies.

### Dedupe at the database boundary

Keeping the decisions in the pure helpers and giving the repository only candidate loading is the right seam, and asserting against exact Hamming distances rather than approximations makes the threshold behaviour verifiable.

`find_duplicate_by_phash` loads every receipt with a non-empty hash into Python and scans linearly. `ix_receipts_image_phash` cannot narrow a Hamming-distance query, so this is O(N) time and memory per ingested receipt with no bound. At Phase 3 volumes that is invisible; it needs a window or a prefix-bucket scheme before it is not.

`mark_duplicate` refuses a self-link and validates both ids exist, but the docstring's reasoning ("a receipt cannot duplicate itself, which would make the chain a cycle") only rules out the length-1 cycle. A→B followed by B→A is accepted, and nothing stops a new receipt from being linked to a receipt that is itself already a duplicate, producing a chain any resolver has to be prepared to walk.

### Export sheets and the date range

Passing per-receipt metadata as a parallel `list[ReceiptExportRow]` rather than ORM rows keeps `export` decoupled from the database and from a live session while preserving every existing call form, and the float conversion stays confined to `_num_cell`/`_ratio_cell` with aggregates computed in `Decimal` first — which is what ADR-0001's display-boundary carve-out actually requires.

The `Summary` date range is the weak spot. `_date_of` prefers `row.txn_date` (documented as an ISO string) and falls back to `receipt.receipt.date`, then sorts the collected strings lexically. But `receipt.date` is not guaranteed ISO — `save_extraction` has an explicit branch for the case where it is unparseable, which is the proof that non-ISO values reach that field. A single `3/4/26` sorts after every `2024-…` value and becomes `date_to`.

Smaller: `total_value` writes `0.00` when there are entries but none has a total, and `_finalize` puts an autofilter across the whole `Summary` used range, spanning the `status` and `merchant` section headers — cosmetic, but it makes the dropdowns meaningless on that sheet.

### Test coverage

389 tests, all offline on SQLite, with the `PRAGMA foreign_keys=ON` fixture repeated consistently so cascade behaviour is exercised rather than assumed. The tests carrying the most weight are the ones asserting silence: redaction leaving money, hashes, and last4 untouched; dedupe returning `None` for a NULL total; `apply_corrections` writing zero rows for a no-op patch; the review sheet header-only with no metadata. The migration suite disposes engines in `finally` blocks, which is what keeps it green on Windows.

Not tested: PAN shapes beyond the three canonical ones (no period-prefixed case, no mixed separators, no PAN-as-dict-key, no `float`/`set` input); non-finite Decimals anywhere on the money path; any string exceeding a `String(n)` column length, which SQLite cannot fail on and therefore cannot be caught offline at all; `mark_duplicate` 2-cycles; a line-item position swap through `apply_corrections`; `enqueue_review` with a negative priority; the `enqueue_review` insert race (untestable in-process, but a comment marking the single-writer assumption would help); and `compare_metadata` for anything Postgres-only.

The ORM float guard walks `Base.metadata` for `isinstance(column.type, sa.Float)`, which is the right structural idea but checks only the type class. A money column declared `Numeric(14, 4, asdecimal=False)` returns Python floats and passes.
